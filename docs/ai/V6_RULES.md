# V6 — Enterprise engineering rules (mandatory for code changes)
Read this file for every task that changes source. Preserve project-specific AGENTS rules, user scope and V5 continuity/UI workflows. If rules conflict, use the stricter safety rule and report the conflict. Read only the relevant skill and stack profile. See V6_MODES.md for routing.

## Baseline and scope
Establish acceptance criteria, Git status (if available), affected trust boundaries, existing tests and risks. Preserve user changes. Use Graphify scoped queries for cross-module discovery; verify source. Never ingest entire graph or repeatedly audit the whole repo. Isolated edits can skip graph discovery. Record evidence after meaningful checkpoints in existing task state/handoff; never replace existing task data. Do not start unrelated work. For legacy audits produce a prioritized remediation backlog, not an unbounded rewrite.

## Mandatory engineering gates
- Every endpoint: explicit public/private classification; authentication where required; server-side authorization on action AND object/tenant; reject unauthorized field changes; validate path/query/body/files using allowlists, types, size and bounds. Never trust client-supplied role, tenant, owner, price or computed totals. Default deny. Use framework CSRF protection for cookie-authenticated state changes, explicit CORS origins where needed, abuse controls and safe HTTP verbs. Public webhooks need signature, replay and idempotency checks where applicable.
- Controllers are transport adapters: validated input, authorization, use case call, response mapping. Do not pass arbitrary request bodies into ORM or serialization. Services enforce business invariants and resource authorization even when invoked by jobs/CLI where applicable. Keep model persistence and domain logic coherent; parameterize queries, allowlist assignments and output, scope every tenant-bound operation including exports/jobs/cache. DB constraints enforce invariants; transactions cover atomic writes, rollback on failure; handle races with suitable locks/unique constraints/versioning.
- Exceptions: central handler/filter/middleware maps expected errors to safe responses and appropriate status codes; catch locally only to recover, translate with cause, compensate, retry bounded transient failures or clean up. No blanket catches, swallowed errors or catch-and-return-success. Roll back and propagate unexpected exceptions. Log once at appropriate boundary, with request correlation and redaction. Never expose stack traces, SQL, tokens or personal data to clients.
- Architecture: follow framework conventions, clear responsibilities, explicit module interfaces, dependency injection where useful. Prefer modular monolith before distributed architecture unless evidence warrants change. Patterns require problem, alternatives, tradeoffs, test and ADR for material decisions. No forced repository/service/DTO layers for trivial CRUD; no speculative microservices.
- Security: assess applicable OWASP ASVS controls; record exact version and requirement IDs after verification. Cover injection, XSS, access control/IDOR, CSRF, SSRF, uploads, session/token security, secrets, dependency risks, safe logs, filesystem paths, mass assignment, deserialization and tenant isolation as applicable. Use supported framework primitives. No production probing or destructive commands without authorization.
- Performance/reliability: bounded pagination, inspect N+1 and query plans, measure before cache/index changes; explicit cache scope/invalidation, job timeouts/retries/backoff/idempotency, external call timeouts, consistency and recovery. Do not claim scale without load evidence.
- Quality: run relevant configured lint/format/static analysis, tests including negative authorization/validation/error paths, regression/build checks. Record commands, exit codes, evidence and untested scope. Never disable tests or security checks to pass. Record pre-existing failures separately. No unverified claims.
- Marketplace: preserve readable, configurable source; verify current category-specific rules and rights to redistribute dependencies/assets. English buyer-facing docs, installation/upgrade/uninstall as applicable, clean package and reproducible clean install; no secrets, private data, debug artifacts, hidden callbacks or undisclosed external dependencies. Do not self-certify marketplace approval.

## Gate outcome
Use docs/engineering/QUALITY_GATE.md as checklist and gate-evidence.json for the current task. PASS only with applicable evidence; FAIL/UNVERIFIED blocks done/release for required controls; N/A requires a reason. Record deviations and owner/action; security-critical failures cannot be waived by an AI. The checker validates the record only, not the software. For audit-only requests do not change application source. Report blockers and preserve scope.
